# راهنمای سیستم کاربران و نشست‌ها

## سیاست ورود

هر کاربر فقط یک نشست فعال دارد. ورود دوم با 409 رد می‌شود تا نشست قبلی خارج یا منقضی شود.
این سیاست روی دیتابیس اعمال می‌شود، نه با غیرفعال‌کردن دکمهٔ ورود.
تمام تغییرات نشست ابتدا رکورد کاربر را با SELECT FOR UPDATE قفل می‌کنند.
یک ایندکس یکتای شرطی نیز از ثبت دو نشست لغونشده برای یک کاربر جلوگیری می‌کند.
نشست منقضی‌شده هنگام ورود بعدی لغو می‌شود.

## مسیرها

| مسیر | ورودی | نتیجه |
| --- | --- | --- |
| POST /users/register | JSON شامل username، email، password، re_password و phone_number اختیاری | کاربر جدید با نقش user؛ 201 |
| POST /users/login | فرم username و password؛ username می‌تواند ایمیل یا تلفن نیز باشد | جفت توکن، سه کوکی و نشست جدید |
| POST /users/token/refresh | کوکی refresh_token یا JSON شامل refresh_token | جفت توکن جدید در همان نشست |
| POST /users/logout | کوکی‌ها یا هدر Bearer | ابطال نشست و پاک‌کردن کوکی‌ها |
| POST /users/change-password | old_password، new_password، re_new_password | تغییر رمز و ابطال نشست‌ها؛ نیاز به ورود مجدد |
| POST /profile/my-profile | اطلاعات پروفایل | ایجاد یا تکمیل پروفایل صرفاً دارای عکس |
| PATCH /profile/my-profile | فقط فیلدهای مورد ویرایش | ذخیرهٔ تغییرات و website |
| GET /profile/my-profile | احراز هویت | اطلاعات پروفایل |
| POST /profile/avatar | multipart با فیلد data | ذخیرهٔ تصویر PNG |

/login2 برای سازگاری باقی مانده ولی دقیقاً همان منطق /login را اجرا می‌کند و در مستندات نمایش داده نمی‌شود.
مسیرهای اشتباه /usersregister و /profilemy-profile دیگر استفاده نمی‌شوند.

## کوکی، هدر و CSRF

کوکی‌های access_token و refresh_token از نوع HttpOnly هستند.
کوکی csrf_token توسط جاوااسکریپت خوانده می‌شود. در درخواست‌های تغییردهندهٔ وضعیت که از کوکی استفاده می‌کنند،
مقدار آن را در هدر X-CSRF-Token بفرست؛ از جمله refresh، logout، change-password و ویرایش پروفایل.
در Swagger مقدار این هدر در ورودی endpoint قرار می‌گیرد؛ مقدار را از کوکی csrf_token مرورگر بردار.
نبود یا اشتباه‌بودن هدر، پاسخ 403 می‌دهد.

برای مشتری غیربرنامهٔ مرورگر، Access Token را در Authorization: Bearer ارسال کن.
Refresh Token نیز می‌تواند در JSON ارسال شود؛ اگر کوکی refresh_token موجود باشد، کوکی اولویت دارد و CSRF لازم است.
فقط مسیرهایی که صریحاً هدر Bearer را می‌خوانند از آن استفاده می‌کنند؛ refresh همچنان به خود Refresh Token نیاز دارد.
توکن‌ها یا رمز عبور را در لاگ ننویس.

COOKIE_SECURE به‌صورت پیش‌فرض true است. برای توسعه با HTTP محلی، مقدار COOKIE_SECURE=false را
در تنظیمات محیط بگذار. در HTTPS واقعی آن را true نگه دار.
AUTH_ALLOWED_ORIGINS به‌صورت پیش‌فرض خالی است و درخواست هم‌مبدأ پذیرفته می‌شود.
برای رابط روی مبدأ دیگر، لیست صریح مبدأهای مجاز و تنظیم CORS متناسب لازم است؛ این گزینه به‌تنهایی CORS را فعال نمی‌کند.

نمونهٔ اجرا در PowerShell از ریشهٔ پروژه برای HTTP محلی:

```powershell
$env:COOKIE_SECURE = "false"
.\.venv\Scripts\python.exe -m uvicorn main:app --app-dir src --reload
```

## توکن و انقضا

هر توکن sub، sid، jti، token_type، iat و exp دارد.
Access Token با SECRET_KEY و Refresh Token با REFRESH_TOKEN_SECRET_KEY امضا می‌شود؛ کلیدهای قوی و متفاوت تنظیم کن.
نوع توکن و فیلدهای ضروری هنگام خواندن بررسی می‌شوند.
فقط هش SHA-256 توکن refresh در جدول جدید ذخیره می‌شود.

زمان انقضای نشست از زمان ورود و REFRESH_TOKEN_EXPIRE_MINUTES محاسبه می‌شود؛ refresh آن را تمدید نمی‌کند.
Access Token نیز از زمان انقضای نشست جلوتر نمی‌رود.
هر درخواست محافظت‌شده وضعیت کاربر و نشست را بررسی می‌کند؛ بنابراین خروج و تغییر رمز،
توکن‌های قبلی را برای درخواست‌های بعدی فوراً نامعتبر می‌کنند. درخواست در حال اجرا به عقب برگردانده نمی‌شود.

هر Refresh Token فقط یک بار مصرف می‌شود. زمان مصرف و شناسهٔ جایگزین نگه داشته می‌شوند.
استفادهٔ مجدد، کل نشست را باطل می‌کند. به همین دلیل کلاینت باید درخواست refresh را مشترک و تک‌اجرا نگه دارد؛
دو تب یا دو درخواست نباید هم‌زمان یک Refresh Token را مصرف کنند. retry کورکورانه نیز مناسب نیست.

## دیتابیس و سازگاری

Migration a8c193d5e270 دو جدول tblAuthSessions و tblRefreshCredentials را اضافه می‌کند.
جدول قبلی tblRefreshToken و داده‌هایش حذف نشده‌اند، اما در احراز هویت جدید استفاده نمی‌شوند.
توکن‌های قدیمی بدون sid و token_type پذیرفته نمی‌شوند؛ بعد از ارتقا ورود دوباره لازم است.
نقش کاربران قدیمی عمداً تغییر نکرده است؛ پیش‌فرض ثبت‌نام جدید user است.

برای نصب دیگری از پروژه، از پوشهٔ src اجرا کن:

```powershell
..\.venv\Scripts\python.exe -m alembic upgrade head
```

سوابق مصرف توکن را تا پایان عمر نشست نگه دار. پاک‌سازی دوره‌ای سوابق منقضی‌شده به‌صورت خودکار در این پروژه فعال نیست.
محدودکردن نرخ درخواست و مقابله با تلاش‌های مکرر ورود نیز باید در لایهٔ سرویس/دروازهٔ استقرار اضافه شود؛
محدودیت یک نشست فعال جایگزین آن نیست.

## تست

از ریشهٔ پروژه:

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

تست‌های PostgreSQL با متغیر RUN_POSTGRES_AUTH_TESTS=1 فعال می‌شوند.
آن‌ها روی سرور تنظیم‌شده یک schema تصادفی موقت می‌سازند و فقط همان schema را پاک می‌کنند.
به جدول‌ها و کاربران واقعی دست نمی‌زنند.

## اصلاحات خروج و روش ارسال توکن

اگر کوکی Refresh نامعتبر باشد، خروج کوکی Access را نیز بررسی می‌کند؛ ابطال نشست با کوکی همچنان نیازمند CSRF است.
درخواست refresh بدون کوکی و با JSON، فقط JSON برمی‌گرداند و کوکی جدیدی تنظیم نمی‌کند.
در حالت کوکی، تنظیم کوکی‌های جدید و بررسی CSRF مانند قبل انجام می‌شود.
نام کاربری عددی نیز قابل ورود است. اگر شناسهٔ ورودی هم نام کاربری یک حساب و هم شماره تلفن حساب دیگر باشد،
پاسخ 400 داده می‌شود و باید از ایمیل استفاده کرد؛ سیستم حساب را حدس نمی‌زند.
